## 后续：面板卡顿排查与 `--software-rendering`（2026-10-15）

起点是用户报告：已安装的面板在打开、拖动、点击时持续低帧率、不跟手；拖动时一直是低帧率，
不是停顿数秒。进程在检查时 Responding 为 true，没有崩溃日志。

已经做到的：

- 桌面自动化检查覆盖了一部分交互：真实面板打开成功，切换“已用 / 剩余”成功且界面立即
  更新，拖动成功，设置窗口能打开。
- 补充了应用内 `--software-rendering` 开关（仅设置
  `RenderOptions.ProcessRenderMode = SoftwareOnly`），用于在目标机器上做 A/B。

仍然未知，且不能从上面的记录推断：

- 拖动时的**实际帧率**没有测量，因此“是否掉帧、掉到什么程度”没有结论；自动化操作耗时
  不是帧延迟证据。
- 设置窗口保存后关闭、关闭主面板隐藏到托盘、退出、开机自启注册表都未单独验收。
- 持续拖动低帧率的根因仍待确认；刷新时的界面线程阻塞已定位并修复（见下方模拟测试）。
- WPF + 可变刷新率显示器（G-Sync / FreeSync 类驱动在合成时压低刷新率，参见
  dotnet/wpf#2294）是一个**可检验假设**，不是结论；`--software-rendering` 只是把这个
  变量从比较中拿掉的手段。
- 没有关闭或修改任何全局 GPU 设置，也没有写注册表；开关仅对单次进程生效，切换需要退出
  正在运行的托盘实例后重启（应用是单实例的）。

### 合成（非拖动 FPS）测量

以下数字来自进程内的回归夹具：用**合成的 fake provider** 让刷新在 UI 线程上跑出一段
同步前缀，然后测量 UI 线程被占住多久、以及同一时间窗口内 UI 心跳还能跑多少次。它衡量的是
**同步阻塞时长**，**不是**拖动帧率、不是面板 FPS，也不是真实账号或真实网络的耗时。

| 指标 | 修复前 | 修复后 |
| --- | --- | --- |
| 单次刷新占用 UI 线程（fake provider、后台 I/O 修复前后） | 611 ms | ~0 ms（低于计时/取整精度） |
| 600 ms fake 前缀窗口内 UI 心跳次数 | 0 | 19 |

这组数字说明的是“刷新路径会在 UI 线程上阻塞”，属于交互触发的停顿；它**不能**解释用户
报告的“拖动时持续低帧率”，两者可能是不同的问题。验证结果：Debug 构建 0 warning /
0 error；Core 自动检查 56/56，界面逻辑检查 30/30，合计 86 项。

验证方式说明：`RenderTargetBitmap` 冒烟测试只覆盖视图布局与像素输出，**不是**拖动或
帧率验证，不能用来声称交互流畅。上述交互记录来自桌面自动化，也不能当作帧率证据。
